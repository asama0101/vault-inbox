> 注記: この SPEC は設計時のもので、実装と差がある（`tags` は廃止。資料ごとのノートの代わりに、md のプロパティと `<資料名>.要約.md` を使う。`_index.md` は作らず、旧版の分は削除する）。基準は実装（README と各 SKILL.md）。

## 概要

Obsidian の Vault をルートとして動く Claude Code プラグイン `vault-inbox` を作る。日々の資料（受領・作成・参照したもの）を、利用者が `inbox/` に入れ、コマンドで整理する。利用者の問い合わせには、格納した資料から回答を作る。回答のたびに、見つけた資料同士の関係を、利用者が承認したものだけ記録し、次の回答の材料に使う（承認された関係の分だけ、精度が上がっていく）。

形式的な処理（取り込み・テキスト抽出・振り分けの実行・索引・目次・追従）は Python のスクリプトに、不確定な判断（要約・分類先・関係の発見・回答の作成）は SKILL.md 等に任せる。

「自動的に整理」は、次の 2 つのコマンドで実現する。`/vault-inbox:organize` は、実行した時点の `inbox/` と整理済みフォルダの状態を、1 回だけ調べて整理する。`/vault-inbox:watch` は、Claude Code のセッション内で `inbox/` と整理済みフォルダを常時監視し、変化を検知したら、実行を始めるための確認なしで、`organize` と同じ処理を自動で実行する（処理の中の、分類先などの選択式の確認は、これまでどおり出る）。どちらも、利用者が実行（起動）したときだけ動く（セッション開始時の自動実行・自動起動はしない）。資料の格納は、利用者が行う（会話で参照・作成した資料の自動格納はしない）。

### 入力
依頼文の要約:
- 目的: 日々の、受領した資料・作成した資料・参照した資料を `inbox` に格納すると、自動的に整理される。利用者の問い合わせに対し、格納した資料から回答を作る。
- 精度向上: 回答を作るときに、資料同士の関係性を記録し、精度を上げていく。
- 前提: プラグインを動かすルートディレクトリは、Obsidian の Vault とする。
- 実装方針: 形式的な部分はスクリプトにし、不確定要素は SKILL.md 等に任せる。
- 追加要望（最終確認で）: `watch` のような、常時監視するコマンド。

参考資料: なし（入力ファイルのパス一覧は空）。

### 構成
- プラグイン名: `vault-inbox`。コマンドは `/vault-inbox:init`・`/vault-inbox:organize`・`/vault-inbox:watch`・`/vault-inbox:ask`。
- スクリプトは Python（標準ライブラリ中心。PDF・Office のテキスト抽出だけ外部ライブラリ）。
- Vault のルートは、コマンドを実行したカレントフォルダとする。`/vault-inbox:init` は、カレントフォルダに `.obsidian/` がなければ、AskUserQuestion の選択肢（続行する・やめる）で確認する。`/vault-inbox:organize`・`/vault-inbox:watch`・`/vault-inbox:ask` は、`inbox/` と `.vault-inbox/` がカレントフォルダになければ、何もせず、`init` を実行するよう知らせる。
- Vault 内のフォルダ:
  - `inbox/`: 利用者が資料を直接置く場所（サブフォルダは使わない）。
  - `project/<プロジェクト>/<分類>/…`: プロジェクトの資料。
  - `shared/<種類>/<サブ>/…`: 特定のプロジェクトに属さない資料。
  - 整理済みの原本は、分類先のフォルダに、通常のファイルとして直接置く。名前も内容も変えない。資料ごとのノートは作らない。
  - `.vault-inbox/`: 内部ファイル。Obsidian は読み込まない。次の 3 種類を持つ。
    - メタデータ: 各資料の `id`・`hash`・場所・日付・タグ・要約と、関係、承認された関係の種類（語彙）。原本からは作り直せないため、検索の索引とは別に保存する。
    - 全文検索の索引（SQLite FTS5、trigram）。作り直せる。
    - 抽出した全文（`text/`、`.txt`）。原本から作り直せる。
  - `project/` と `shared/` の各フォルダの `_index.md`: 目次ノート。そのフォルダの資料への `[[リンク]]`、サブフォルダの `_index.md` へのリンク、そのフォルダの資料に関する関係（原本への `[[リンク]]`）を書き出す。そのフォルダの資料に関する関係だけを書き、関係は、起点側と行き先側の、両方のフォルダに書く。`_index.md` は、追従・`watch`・取り込みの対象にしない。メタデータから自動で作り直すので、手で書いた内容は、次の整理で上書きされる。
- 深さの上限は、ルート直下のフォルダ（`project/`・`shared/`）を 1 階層として、最大 5 階層（例: `project/案件X/設計/要件/2026/` が 5 階層）。5 階層を超える新しいフォルダは作らず、5 階層目のフォルダに置く。
- 対象の資料: Markdown（`.md`）・テキスト（`.txt`）・HTML（`.html`）・PDF・Office（`.docx`・`.xlsx`・`.pptx`）。
- 次の項目は、利用者の決定事項ではなく、実装計画で決める: `id` の形式、`hash` のアルゴリズム、メタデータの保存形式、外部ライブラリの選定と導入方法、スクリプトのサブコマンドと、Claude の判断結果をスクリプトに渡す形式、コマンド・スキルのファイル構成、`/vault-inbox:ask` で読む資料の数・文字数の上限、`watch` が Monitor に流す検知の方法・間隔・変化が落ち着くまでの待ち時間、書き込み途中のファイルと、人が資料を動かしている途中の状態の扱い、`watch` と `organize` の排他の仕組み。

### 資料のメタデータ
- 各資料について、`id`（資料の識別子）、`hash`（原本の内容のハッシュ）、場所（Vault のルートからのパス）、`date`（文書内の日付、なければ取り込んだ日。複数あるときの選び方は Claude の判断）、`tags`、`summary`（1〜2 文）を、`.vault-inbox/` のメタデータに保存する。
- 資料の区分（受領・作成・参照）と `source` は付けない。
- 原本の内容が変わったとき（場所が同じで `hash` だけ変わった）は、`hash`・全文・索引を更新し、要約・タグ・日付を Claude が作り直す。
- `tags` は、既存のタグを、できるだけ再利用する（表記ゆれを避ける。方針は SKILL.md に書く）。`date` は、`ask` の回答で、資料の新しさを示すために使う。

### 関係性
- 関係は、（起点の資料、行き先の資料、種類）の 1 件として、メタデータに保存する。`_index.md` に、原本への `[[リンク]]` として書き出すので、Obsidian のバックリンク・グラフでも辿れる（Obsidian が開けない形式の資料は、ファイル名のテキストで書く）。
- 種類は固定の語彙。起点から行き先への向きは、`derived_from`（起点は派生した側、行き先は元）、`supersedes`（起点は新版、行き先は置き換えられた旧版）、`supports`（起点は根拠を示す側、行き先は根拠づけられる側）、`conflicts_with`（矛盾。向きなし）、`related`（その他の関連。向きなし）。語彙に合わない関係は、Claude が新しい種類を提案し、利用者が承認すれば語彙に足す。
- 記録は、回答のあとに、見つけた関係の候補を AskUserQuestion の選択肢で提示し、承認されたものだけにする。
- 回答のとき、検索で見つかった資料から、直接つながる資料（1 つ先）まで、両方向に辿る。`supersedes` で置き換えられた旧版は、検索で直接当たった場合も、材料から外す。`conflicts_with` でつながる資料は、回答で矛盾として併記する。

## 流れ

1. `/vault-inbox:init`: カレントフォルダ（Vault のルート）に、`inbox/`・`project/`・`shared/`・`.vault-inbox/` を作る。
2. 利用者が、Obsidian（またはエクスプローラー）で、`inbox/` に資料を直接置く。
3. `/vault-inbox:organize` を実行する。実行した時点の状態を、1 回の実行で、次のとおり処理する（`watch` も、この処理を自動で呼び出す）。最初に、索引と全文が欠けている、または壊れているときは、メタデータと原本から作り直す。
   1. 追従: 整理済みのフォルダ（`project/`・`shared/`）で、人が資料を移動・改名・削除・編集したことを、`hash` と前回の場所で見分けて検出し、メタデータ・全文・索引・`_index.md` を更新する。
      - 場所が変わって `hash` が同じ: 移動・改名として、場所を更新する。
      - 場所が同じで `hash` だけ変わった: 同じ資料の更新として、確認なしで更新する。
      - 上記以外で、見分けられない資料は、一覧にして、資料ごとに AskUserQuestion の選択肢で確認する。状態ごとに、出す選択肢は次のとおり。
        - 消えた資料と新しい原本の両方がある（編集しながら移動したと思われる）: 「組み直す」（相手の候補を示す）・「新規として登録する」（旧資料は索引から外す）・「索引から外す」。
        - 消えた資料だけがある（削除された）: 「索引から外す」・「保留する」。
        - 登録のない原本だけがある（人が直接置いた、「索引から外す」で外した、複製）: 「新規として登録する」・「登録しない」。「登録しない」は記録し、内容も場所も変わらないかぎり、以後は確認しない。内容が同じ複製は、確認せず、複製として一覧で 1 回知らせるだけで、登録しない。
        - 「組み直す」は、消えた資料の `id` と関係を新しい原本に引き継ぐ。「新規として登録する」は、新しい `id` で登録する。「索引から外す」は、メタデータと関係を消し、ファイルは削除しない（そのファイルは、次の整理で、登録のない原本として扱う）。「保留する」は、変更せず、次の整理で、また確認する。
        - `_index.md` と、対象外の形式のファイルは、追従の対象にしない。人が `_index.md` を編集・削除しても、資料としては扱わず、次の整理で作り直す。
      - 行き先の資料がなくなった関係は、関係ごとに「消す」「残す」を、AskUserQuestion の選択肢で確認する。
   2. 取り込みと配置: `inbox/` の資料を 1 件ずつ、次の順に処理する。原本を移す前に、メタデータに「配置中」として記録し、移動と登録が終わってから確定する。途中で中断したときは、再実行で「配置中」の資料を見つけ、続きから完了させる（原本が移動前なら移動から、移動後なら登録から）。
      1. スクリプトが、テキストを抽出し、`id`・`hash` を付ける。すでに取り込んだ資料（同じバッチの先に処理した資料を含む）と同じ内容（`hash` が同じ）なら、取り込まず `inbox/` に残し、既存の資料名を知らせる。
      2. Claude（SKILL.md）が、要約・タグ・日付を作り、既存のフォルダを見て分類先（`project/…` か `shared/…`）を選ぶ。合うフォルダがなければ、新しい分類先を提案し、利用者が AskUserQuestion の選択肢で承認する。
      3. スクリプトが、原本を分類先のフォルダへ移し、全文を `.vault-inbox/text/` に保存して、メタデータと索引に登録する。分類先のフォルダに、同じ名前の別の原本があるときは、名前を変えず、取り込まずに `inbox/` に残して、名前の衝突を知らせる。深さの上限を守る。
   3. 目次（スクリプト）: 関係するフォルダの `_index.md` を作り直す。
   4. 取り込めなかった資料（抽出に失敗した、対象外の形式、同じ内容、同じ名前、分類先が承認されなかった）は、`inbox/` に残し、理由の一覧を最後に知らせる。ほかの資料の整理は続ける。
4. `/vault-inbox:watch`: Claude Code のセッション内で、Monitor により、`inbox/` と整理済みフォルダ（`project/`・`shared/`）の変化（新しい資料、移動・改名・削除・編集）を常時監視する。
   1. 起動した直後に、溜まっている分を `organize` と同じ処理（追従を含む）で 1 回整理してから、監視に入る。
   2. 変化を検知したら、実行を始めるための確認なしで、`organize` と同じ処理を自動で実行する。処理の中の、分類先・関係の消去・追従の確認は、これまでどおり AskUserQuestion の選択肢で聞く。
   3. 監視の対象は、`inbox/` と `project/`・`shared/`。`.obsidian/` と `.vault-inbox/` の中の変化は対象にしない。`organize` と `ask` 自身の書き込み（原本の移動、`_index.md` の作成、メタデータの更新、関係の記録）には反応せず、再実行や確認を起こさない。
   4. 変化が落ち着いてから（人が資料を動かしている途中や、書き込み途中の状態を避けるため）処理する。確認の応答を待っている間に来た変化は、溜めておき、確認のあとでまとめて処理する。
   5. 前回の処理から、ファイルの内容（`hash`）も場所も変わっていない、`inbox/` に残った資料（同じ内容・同じ名前・抽出失敗・分類先が承認されなかった資料）は、`watch` が検知しても、再通知・再確認しない（`watch` の起動直後の 1 回と、利用者が手動で `organize` を実行したときは、これまでどおり知らされる）。
   6. `watch` が動いている間に、同じ `watch` の二重起動や、`organize` の手動実行があったときは、後から来た実行を断り、実行中であることを知らせる。
   7. 止めるのは、セッションを閉じるか、Claude Code の標準の停止の操作による。専用の停止コマンドは作らない。
   8. Monitor が使えない環境では、使えないことを知らせて終わり、`organize` を使うよう案内する。
5. `/vault-inbox:ask <問い>`:
   1. 全文検索の索引（trigram）で候補を引く。3 文字未満の語は、保存した全文を直接探して補う。検索で見つかった資料から、関係を両方向に辿った資料と合わせて、Claude が全文を読んで回答を作る。
   2. 回答は会話に出す。回答には、根拠にした資料の原本へのリンク（出典）を付ける。回答は保存しない。
   3. 回答のあと、見つけた関係の候補を AskUserQuestion の選択肢で提示し、承認されたものをメタデータに記録して、`_index.md` を更新する。

## 受入条件

精度が上がったことを測る検証は、この SPEC の対象に含めない。記録した関係が、次の回答の材料に使われること（条件 12）までを確認する。

0. （前提の確認）実装後に、実際の Obsidian の Vault で、次の 2 点を確認する。`_index.md` の `[[リンク]]` が、バックリンクとグラフに出ること。名前が `.` で始まるフォルダ（`.vault-inbox/`）の中のファイルが、Obsidian の一覧・検索に出ないこと。確認できなければ、設計を見直す。
1. `/vault-inbox:init` を実行すると、カレントフォルダに `inbox/`・`project/`・`shared/`・`.vault-inbox/` ができる。すでにあるフォルダ・ファイルは変更しない。カレントフォルダに `.obsidian/` がなければ、続行するかを選択肢で確認し、「やめる」を選ぶと何も作られない。
2. `/vault-inbox:organize`・`/vault-inbox:watch`・`/vault-inbox:ask` を、`inbox/` と `.vault-inbox/` の少なくとも一方がないフォルダで実行すると、何も作られず、`init` を実行するよう知らされる。
3. `inbox/` に、テキストを抽出できる `.md`・`.txt`・`.html`・`.pdf`・`.docx`・`.xlsx`・`.pptx` の資料を置いて `/vault-inbox:organize` を実行すると、取り込めた各資料について、原本が分類先のフォルダに、同じ名前で移り、メタデータ（`id`・`hash`・場所・`date`・`tags`・`summary`）と全文が `.vault-inbox/` に保存される。取り込めた資料は `inbox/` から消える（取り込めない資料は、条件 15・16・17 のとおり残る）。資料ごとのノートは作られない。
4. 原本の内容は変わらない（移動後の原本から計算した値が、移動前の原本から計算した値と、保存した `hash` の両方に一致する）。
5. 作られるフォルダは、`project/<プロジェクト>/<分類>/…` か `shared/<種類>/<サブ>/…` で、`project/`・`shared/` を 1 階層として 5 階層以内。深さの上限を守る処理（スクリプト）に、6 階層以上の分類先を渡すと、新しいフォルダは作られず、資料は 5 階層目のフォルダに置かれる。
6. 新しい分類先は、利用者が AskUserQuestion の選択肢で承認するまで作られない。承認されなかった資料は、`inbox/` に残る。
7. 整理済みのフォルダで、人が原本を別のフォルダへ移動・改名してから `/vault-inbox:organize` を実行すると、メタデータの場所が実際の場所と一致し、関係は引き継がれ、移動前のフォルダの `_index.md` からは外れ、移動後のフォルダの `_index.md` に載る。場所が同じで内容だけ変えた原本は、確認なしで、`hash`・全文・要約が更新される。
8. 見分けられない資料は、`/vault-inbox:organize` が一覧にして、資料ごとに、状態に応じた選択肢（流れ 3.1）で確認する。選ばれるまで、確認待ちの資料は変更しない（ほかの資料の追従は進む）。選ばれたあとの状態は、「組み直す」は消えた資料の `id` と関係が新しい原本に引き継がれ、「新規として登録する」は新しい `id` で登録され、「索引から外す」はメタデータと関係が消えてファイルは残り、「登録しない」は以後、内容も場所も変わらないかぎり確認されず、「保留する」は変更されない。内容が同じ複製は、登録されず、複製として 1 回知らされる。`_index.md` を人が編集・削除しても、確認は出ず、次の整理で作り直される。
9. 資料 B の原本を削除する、または「索引から外す」を選ぶと、A から B への関係は、行き先がなくなる。`/vault-inbox:organize` は、その関係を、関係ごとに「消す」「残す」の選択肢で確認する。「消す」は、関係が消え、`_index.md` から外れる。「残す」は、そのまま残る。
10. `/vault-inbox:ask` の回答に、根拠にした資料の原本へのリンク（Obsidian が開ける形式は `[[リンク]]`、それ以外はファイル名のテキスト）があり、指す原本が実在する。回答は保存されない。
11. 関係の候補は、利用者が承認したものだけが、（起点、行き先、種類）としてメタデータに記録され、固定の語彙の種類になる。語彙にない種類は、利用者が承認すれば語彙に足される。記録された関係は、起点側と行き先側の両方のフォルダの `_index.md` に、原本へのリンク（Obsidian が開ける形式は `[[リンク]]`、それ以外はファイル名のテキスト）として書き出される。
12. 資料 A から B への関係を記録したあと、B だけに当たる語で `/vault-inbox:ask` すると、A の内容が、回答の材料（出典）に出る。`supersedes` で置き換えられた旧版は、検索に直接当たっても、材料に出ない。`conflicts_with` でつながる資料は、矛盾として回答に併記される。A→B→C の順に関係を記録し、A だけに当たる語で聞くと、B は材料に出るが、C は、検索に当たらないかぎり出ない。検索結果が 0 件のときは、該当する資料がないと答え、推測では答えない。
13. 2 文字の語（例: 「契約」）と、3 文字以上の語の両方で、日本語の部分一致により、資料を検索できる。
14. `project/` と `shared/` の各フォルダに `_index.md` ができ、そのフォルダ直下の資料へのリンク（Obsidian が開ける形式は `[[リンク]]`、それ以外はファイル名のテキスト）と、サブフォルダの `_index.md` へのリンクと、そのフォルダの資料に関する関係の一覧が入る。`inbox/` には作られない。
15. 抽出に失敗した資料と、対象外の形式（`.doc`・`.xls`・`.ppt`・画像など）は、`inbox/` に残り、理由の一覧が知らされ、ほかの資料の整理は続く。
16. すでに取り込んだ資料と同じ内容の資料は、取り込まれず `inbox/` に残り、既存の資料名が知らされる。`/vault-inbox:organize` を再実行しても、取り込み済みの資料は二重に登録されない。
17. 分類先のフォルダに、同じ名前で内容が違う原本があるときは、名前は変えられず、取り込まれずに `inbox/` に残り、名前の衝突が知らされる。
18. `/vault-inbox:watch` を起動すると、起動した直後に、`inbox/` に溜まっていた資料の整理と、整理済みフォルダでの追従が、`organize` と同じ処理で行われる。
19. `watch` の起動中に、`inbox/` に資料を置く、または整理済みフォルダで資料を移動・改名・削除・編集すると、利用者がコマンドを実行しなくても、実装計画で決める待ち時間が経過したあとに、`organize` と同じ処理が実行され、条件 3・7・8・9 と同じ結果になる。確認が要る場合は、選択肢で聞かれる。同じ変化が重複して検知されても、結果は同じ（二重に登録・確認されない）。
20. `watch` は、`organize` と `ask` 自身の書き込み（原本の移動、`_index.md` の作成、メタデータの更新、関係の記録）には反応せず、`.obsidian/` と `.vault-inbox/` の中の変化も処理しない。`inbox/` に残った資料は、`hash` も場所も変わらないかぎり、`watch` が検知しても再通知・再確認されない。確認の応答を待っている間に来た変化は、確認のあとでまとめて処理される。
21. `watch` の起動中に、`watch` の二重起動や `organize` の手動実行をすると、後から来た実行は断られ、実行中であることが知らされる。`ask` の関係の記録（メタデータへの書き込み）は、`organize`・`watch` の処理が終わるまで待たされる。排他の印が残ったとき（異常終了のあと）に、断られ続けないことは、実装計画で決める（期限切れ・生存確認など）。
22. セッションを閉じる、または Claude Code の標準の停止の操作をすると、`watch` は止まり、以後の変化は、`organize` または `watch` を実行するまで処理されない。
23. `/vault-inbox:ask` で、記録を提案する関係の候補が 0 件のときは、何も聞かずに終わる。
24. `.vault-inbox/` の索引と全文を消して `/vault-inbox:organize` を実行すると、メタデータと原本から作り直され、`/vault-inbox:ask` の検索が、消す前と同じ結果になる。
25. Monitor が使えない環境で `/vault-inbox:watch` を実行すると、使えないことが知らされ、`organize` を使うよう案内される。

## 非目標

利用者が選んだ案に含まれないため、対象外とするもの:
- 資料ごとの Markdown ノート（frontmatter にメタデータと関係を書く形）。メタデータと関係は、`.vault-inbox/` に持つ。
- 画像・音声の文字起こし・OCR。
- Office の旧形式（`.doc`・`.xls`・`.ppt`）の対応。
- 資料の区分（受領・作成・参照）と `source` の記録（付ける必要が分からないため）。
- 重複の統合の提案（同じ内容の資料を取り込まないことだけを行う）。
- 埋め込みベクトルによる意味検索。
- セッション開始時の自動整理・`watch` の自動起動・件数の通知。
- Claude Code を閉じたあとも動く常駐の監視（別プロセスの常駐スクリプト）、`watch` の専用の停止コマンド、監視対象の設定、整理の履歴のログ。
- コマンドでの外部資料の取り込み、会話中の資料の自動格納（資料は、利用者が `inbox/` に直接置く）。
- 回答のノートとしての保存。
- フォルダ名の設定による変更。
- `.vault-inbox/` の検査・修復のコマンド、メタデータの形式を変えるときの移行。

## リスク

- Obsidian の次の挙動は、実機で確認していない（受入条件 0 で確認する）: `_index.md` の `[[リンク]]` が、バックリンク・グラフに出ること。名前が `.` で始まるフォルダを、Obsidian が読み込まないこと。
- メタデータと関係は、原本から作り直せない。`.vault-inbox/` のメタデータを失うと、関係の記録が失われる。Vault と一緒に、利用者がバックアップする。索引と全文は、作り直せる。
- Obsidian は、既定では、docx・xlsx・pptx などを一覧に出さず、`[[リンク]]` も辿れない場合がある。`_index.md` では、その形式の資料を、ファイル名のテキストで書く。
- `.vault-inbox/` は隠しフォルダのため、Vault の同期・バックアップの設定によっては、対象から外れる。メタデータの書き込みは、途中で壊れないようにし（直前の版を退避する）、実装計画で決める。
- 内容（`hash`）が同じ資料は、別の資料として持てない（空のファイルや、同じ内容のテンプレートも、2 つ目以降は取り込まれない）。「組み直す」で相手を誤って選ぶと、別の資料に関係が引き継がれ、取り消す手段はない（`.vault-inbox/` を直接編集するしかない）。
- 整理済みフォルダの `.md` を、Obsidian で編集すると、`watch` の起動中は、保存のたびに（待ち時間のあとで）、`hash`・全文・要約の更新が走り、Claude が動く。頻繁に編集する資料は、使用量が増える。人が `_index.md` に手で書いた内容は、失われる。
- `.vault-inbox/` が Obsidian から読み込まれる設定（隠しフォルダの除外を変えた場合）では、抽出した全文が、Obsidian の検索に混ざる。
- すでに `project/`・`shared/` を使っている既存の Vault に導入すると、導入直後に、既存のファイルが「登録のない原本」として、まとめて確認に出る。
- Vault のルートはカレントフォルダとするため、Vault の途中のフォルダで `init` を実行すると、誤った場所に `inbox/` などが作られる。`.obsidian/` がなければ確認するが、利用者が続行を選べば作られる。
- 資料ごとのノートがないため、原本は、`hash` と前回の場所だけで見分ける。編集しながら移動した原本は、見分けられず、確認が要る。確認の件数が多いと、利用者の手間が増える。ほかの承認・確認（分類先・関係・新しい種類）も同じで、一括承認や自動承認はしない。
- 場所が同じで内容だけ変わった原本は、確認なしで同じ資料の更新として扱う。内容が大きく変わっても、関係は残る。
- 索引と全文（`.vault-inbox/`）を Vault ごと同期すると、同期先で衝突する可能性がある。
- 文字が取れない PDF（スキャン）や、壊れた・パスワード付きの資料は、取り込めず `inbox/` に残る。同期中の書き込み途中のファイルも、取り込みに失敗して `inbox/` に残る（再実行で取り込める）。同じ名前で内容が違う原本も、`inbox/` に残る（利用者が名前を変えて、置き直す）。
- 全文を平文で `.vault-inbox/text/` に保存し、回答のとき Claude に全文を読ませる。機密・個人情報を含む資料は、利用者が `inbox/` に置く前に判断する。暗号化・アクセス制御はしない。
- 整理の途中で失敗・中断した場合、原本の移動の巻き戻しはしない。「配置中」の記録があるので、再実行で続きから完了できるが、原本のバックアップは、利用者が取る。
- `watch` は、実行を始めるための確認なしで自動実行するため、利用者が意図しないタイミングで、処理の中の選択式の確認（分類先など）が出る。起動直後に溜まっている分が多いと、確認がまとまって出る。確認は、同じセッションの会話で出るので、`ask` など、ほかの対話と順番に進む。
- 人が資料を動かしている途中（原本を動かした直後など）や、書き込み途中のファイルを検知すると、「見分けられない資料」の確認や取り込みの失敗が出る。変化が落ち着くまで待つが、待ち時間を超える操作では、起こりうる。
- セッションを閉じると、`watch` は止まり、閉じている間の変化は、次の実行まで処理されない。Monitor が使えない環境では、`watch` は動かない。Windows のイベントの取りこぼし、同期フォルダ、ネットワークドライブの変化は、検知できない場合があるが、`organize` を実行すれば拾える。
- `watch` は、変化のたびに Claude が動くので、大量の資料を置く、同期が走るなどすると、Claude の使用量が増える。
- `ask` が検索するのは、メタデータに登録した資料だけで、`inbox/` に残っている未整理の資料や取り込めなかった資料は、回答の対象にならない（件数も知らせない）。
- Windows のパスの長さの上限と、ファイル名に使えない文字に、日本語の長い名前と 5 階層の深さが当たる可能性がある。
- 想定は、単一の利用者・単一の端末。同じ端末での `organize` と `watch` の同時実行は、後から来た実行を断って防ぐ（流れ 4）。複数端末での同時利用と、Obsidian で編集している最中の同期の競合は、扱わない。Obsidian のプラグイン API・Dataview などとの連携も想定しない。
- 外部ライブラリ（PDF・Office の抽出）の導入と、SQLite の FTS5・trigram が使えない環境は、実装計画で確認する。
- 関係の記録は、人が `.vault-inbox/` を直接編集すれば、変えられる。精度が上がったことを測る手段は、この SPEC にはない。
- 既存の Vault にある、`inbox/` 以外の既存のノートは、取り込まれず、整理の対象にもならない。
