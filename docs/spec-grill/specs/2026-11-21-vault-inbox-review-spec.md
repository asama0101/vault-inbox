## 概要

ローカルリポジトリのプラグイン `vault-inbox`（`D:\claude\local-repo\vault-inbox\vault-inbox\`）を、8 手順でレビューし、修正する。ユーザーの承認が要る手順（2・3・6）は、承認を得るまで次へ進まない。レビューの基準は、手順 2 でユーザーが確定した「目的と期待効果」とする。

この SPEC は、依頼（プラグインのレビューと修正）を、受入条件で検証できる形にしたもの。レビュー・修正そのものは、この SPEC の承認後に行う。

### 入力
依頼文の要約:
- 対象: ローカルリポジトリのプラグイン（`vault-inbox` と確認済み）。
- 事前に読む規則: `~/.claude/reference/review.md`・`plugin-rules.md`・`writing.md`（すべて読み済み）。
- 手順: 8 手順（下の「流れ」）。担当は、メイン・スクリプト・サブエージェントに分ける。
- 最終報告: 6 項目（下の「最終報告の形」）。

### 先に分かっている食い違い（手順 5 で確認する論点）

2. 規則 `plugin-rules.md` との差（`plugin.json` と `marketplace.json`、ファイル構成を見た範囲）。
   - `doctor`（A4）、`NOTICE`（C1）、`CLAUDE.md`（D2）、CI（D2）、`allowed-tools`（B3）が見当たらない。
   - `plugin.json` に `repository`・`keywords` がなく、`author.name` が `<名前> contributors` の形でない（D1）。
   - 状態を `.vault-inbox/`（Vault 内）に置く。規則 A1 は `${CLAUDE_PLUGIN_DATA}` を求める。利用者の資料に付随するデータなので、例外とするかを、手順 2 の後に確認する（推測）。
3. `README.md` の未検証表記。インストールコマンドと実行出力が「未検証」とある。規則 E3 は、基本の使い方を新しい環境で実行して確かめることを求める。

## 流れ

1. 手順 1（メイン）: プラグイン内の全ファイルを読み、目的・期待効果・想定利用者の仮説を作る。根拠にしたファイル名を添える。
2. 手順 2（メイン、承認）: AskUserQuestion で「この理解で正しいか」を聞く。選択肢は「正しい」「一部違う」「違う」。違う点は自由記述で受け取り、仮説を直して再確認する。「正しい」を得るまで、レビューにも修正にも進まない。確定した内容を、レビューの基準とする。
3. 手順 3（メイン、承認）: 目的と期待効果、使い方（呼び出し方・入力と出力の例）、処理の流れの図、ファイル構成と役割の表、インプットファイルとアウトプットファイルを、Artifact（HTML）で提示する。開いたあと、AskUserQuestion で「レビューを始めてよいか」を聞く。修正の依頼があれば、更新して再確認する。
4. 手順 4（スクリプト）: 機械的に判定できる検査を、作業用フォルダ（スクラッチパッド）のスクリプトで行う。プラグイン本体には、ユーザーが頼んだとき以外は入れない。出力は、ファイル・行・検査名・結果（OK/NG）の JSON。実行して結果を保存する。
5. 手順 5（サブエージェント 3 体、並行）: 新規で起動する（fork しない）。メインの結論は渡さない。

   | 体 | 担当 | 観点（`review.md` の番号） |
   |---|---|---|
   | A | 目的に合うか、漏れ・矛盾がないか | 1・3・4・7 |
   | B | 誤り・安全性・過剰な作り・保守性 | 2・5・6・8・10 |
   | C | 反証。「なぜ目的を達成できないか」だけを探す。改善案は出さない。A・B の指摘は渡さない | Red Review |

   メインは、3 体の指摘とスクリプト結果を統合し、Critical・High・Medium・Low に分類する。
6. 手順 6（メイン、承認）: HTML がある場合だけ行う。現状のスクリーンショットと、変更案（配色・レイアウト・文字サイズ・前後の比較）を、表示幅 800px と 375px で示す。AskUserQuestion で「案 A（推奨）」「案 B」「変更しない」から選ばせる。承認された案だけを手順 7 で反映する。
7. 手順 7（サブエージェント）: レビュー担当とは別の新規サブエージェントで修正する。Critical → High の順に、1〜3 件ずつ渡す。Medium・Low は、ユーザーが望んだときだけ直す。変更は、指摘に直接つながる行だけにする。機械的な修正はスクリプトで行う。
8. 手順 8（スクリプト＋サブエージェント）: 手順 4 を再実行し、修正した部分を新規のサブエージェントに再レビューさせる。Critical = 0 かつ High = 0 で終了する。満たさなければ手順 7 に戻る。同じ部分につき 3 周までとし、超えたら直さず「既知の穴」として報告する。

### 手順 4 の検査項目
| 検査名 | 内容 | 対象 |
|---|---|---|
| json_syntax | JSON の構文、必須項目、バージョンの整合 | `plugin.json`・`marketplace.json`・コード中の version |
| frontmatter | `name`・`description` の有無、`name` とフォルダ名の一致 | 4 つの `SKILL.md` |
| path_exists | 文書が参照するファイル・パスの実在、`${CLAUDE_PLUGIN_ROOT}` の指す先 | `SKILL.md`・`README.md` |
| unreferenced | どこからも参照されないファイル | プラグイン全体 |
| secrets | トークン・パスワード・個人のパスの混入（パターン検索） | リポジトリ全体（`.venv/` を除く） |
| readme_diff | `README.md` と実際のファイル構成の差 | `README.md`・`git ls-files` |
| html_external | HTML の外部 URL 読み込み、script の有無 | HTML・SVG（現状 `docs/images/how-it-works.svg` など） |
| rules_e1 | `plugin-rules.md` E1 の 1〜7（絶対パス・`${CLAUDE_SKILL_DIR}`・相対リンクの有無、git 管理、`claude plugin validate --strict`） | プラグイン全体 |

### 最終報告の形
1. 確定した目的と期待効果（1〜2 文）
2. 指摘の一覧（重要度順。重要度・観点・場所・内容・修正案）と、各指摘の対応（修正済み／未対応）
3. スクリプトの検査結果（修正前と修正後の NG 件数）
4. 対象外にした観点（理由つき）
5. 収束判定（Critical と High の残数、終了できる／できない）
6. 変更したファイルの一覧（絶対パス）

## 受入条件

1. 手順 2 で、ユーザーが「正しい」を選ぶまで、手順 3 以降（スクリプト検査・レビュー・修正）を実行していない。
2. 手順 1 の仮説の各項目に、根拠にしたファイル名が付き、推測は「推測」と書かれている。
3. 手順 3 の Artifact に、目的と期待効果・使い方・処理の流れの図・ファイル構成と役割の表・インプットとアウトプットの 5 つが載っている。ユーザーが「レビューを始めてよい」を選ぶまで、手順 4 以降へ進んでいない。
4. 手順 4 のスクリプトは、スクラッチパッドに置かれ、プラグイン本体（`vault-inbox/`）には追加されていない（ユーザーが頼んだ場合を除く）。出力は、ファイル・行・検査名・結果を持つ JSON で、保存されている。
5. 手順 5 の 3 体は、すべて新規のサブエージェントで、依頼文に、対象のパス・確定した目的と期待効果・手順 4 の結果・担当する観点が書かれている。C の依頼文に、A・B の指摘と、メインの結論がない。
6. 手順 5 の指摘が、重要度・観点・場所・内容・修正案の形で返り、関係しない観点には「対象外: 観点名（理由）」が付いている。
7. HTML がある場合、手順 6 で、現状のスクリーンショットと変更案が 800px と 375px の両方で示され、ユーザーが選んだ案だけが反映されている。デザインを変える修正は、承認前に行われていない。
8. 手順 7 の修正は、レビュー担当とは別の新規サブエージェントが行い、Critical → High の順に、1〜3 件ずつ渡されている。変更した行のすべてが、いずれかの指摘に直接つながる。Medium・Low は、ユーザーが望んだものだけ直され、残りは報告に書かれている。
9. 手順 8 で、手順 4 のスクリプトが再実行され、修正前後の NG 件数を比べられる。再レビューは、新規のサブエージェントが行っている。
10. 終了は、Critical = 0 かつ High = 0 のときだけ。同じ部分が 3 周で収束しないときは、直さずに「既知の穴」として報告されている。
11. サブエージェントを起動できないときは、レビューせずに、「未レビュー」と理由が報告され、収束判定は書かれていない。
12. 最終報告に、上の 6 項目がすべてあり、変更したファイルの一覧は絶対パスで書かれている。
13. 判断を仰ぐ質問は、すべて AskUserQuestion の選択肢で行われ、推奨案に「(推奨)」が付いている。
14. 最終報告の文章が、`writing.md` の規則（結論が先頭、図・表の活用、数字の照合、載せてはいけない情報がない）に合っている。

## 非目標

依頼に含まれないため、対象外とするもの:
- プラグインの機能追加と、設計 SPEC の変更（食い違いの解消方針は、手順 2 でユーザーが決める。決めた方向への修正だけを行う）。
- Medium・Low の指摘の修正（ユーザーが望んだ場合を除く）。
- `.venv/`・`.pytest_cache/`・`__pycache__/` など、依存や生成物の中身のレビュー。
- コミット・プッシュ・PR の作成（依頼にない。必要なら、修正後に別途聞く）。
- Claude Code での実機の動作確認の完全な実施（実行できなかった項目は「未検証」と報告する）。

## リスク

- 設計 SPEC と実装の食い違いが大きいと、「目的に合うか」の基準が 2 つになる。手順 2 で、どちらを基準にするかを決めないと、指摘が割れる。
- 手順 2・3・6 の承認待ちで、作業が止まる。ユーザーが不在のあいだは進まない。
- `vault-inbox/` の Python（約 1,900 行）と、`SKILL.md`（約 210 行）が対象。3 体のレビューで、同じ指摘が重複する可能性がある。統合時に整理する。
- 修正が、原本の移動・削除・ロックに関わる箇所に及ぶと、既存の動作を壊すおそれがある。再検査の前に、テスト（`vault-inbox/tests/`）を実行する。実行環境（`.venv`、Python 3.14 の記録がある）で動かせない場合は、「未検証」と報告する。
- `claude plugin validate --strict` が、この環境で動かない可能性がある。その場合は、E1 の 7 を「未検証」と報告する。
- サブエージェントに渡す依頼文に、ユーザーの個人情報（メールアドレスなど）を入れない。
- 同じ部分で 3 周しても収束しない指摘が残る可能性がある（既知の穴として報告する）。
